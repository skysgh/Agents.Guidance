# Architects

Architects make the wider service understandable and establish the boundaries, dependencies and responsibilities that later work must respect. This route currently uses the established foundation pages as its canonical detailed guidance.

## A useful way into the route

[Guidance for System Design Architects](../../../foundations/guidance-for-system-design-architects.md) is the main route into the whole-system map, conceptual/logical/physical distinction, platforms, sites, dependencies, LDMs and architectural handoff. The [Stakeholder Roles](../../../shared/reference/catalogues/stakeholder-roles.md), [Users to Consider](../../../shared/reference/catalogues/users.md) and [System Roles](../../../shared/reference/catalogues/system-roles.md) catalogues add the perspectives, authority and access contexts that the map needs to keep visible. [Shared Requirements](../../../shared/requirements.md) helps connect analysis and product decisions to architecture, while its [specialist controls](../../../shared/requirements.md#specialist-controls-enable-the-outcome-and-protect-it-when-needed) section identifies the specialist evidence the architect must integrate. [Guidance for Tech Leads](../../../foundations/guidance-for-tech-leads.md) becomes a natural next conversation when the map is ready to become implementable structure. When conceptual language starts to blur identities and relationships, [Entity Lifecycle Patterns](../../../shared/reference/catalogues/entity-lifecycle-patterns.md) offers a more focused way to think it through.

## The architect's responsibility

The architect integrates stakeholder, product, domain and specialist technical input into a coherent system map. The architect does not become the universal SME for Operations, Maintenance, Monitoring, Change Control, Security, Privacy, Records, assurance, Support, Supplier or Delivery responsibilities merely because those concerns affect the architecture.

A route is ready for technical leadership when it makes boundaries, dependencies, authority, assumptions, omissions and required evidence visible. It need not prescribe every class, provider option or project folder.

Architecture must distinguish what retains identity and responsibility across changing arrangements from what records a bounded membership, appointment, assignment, decision or interaction. This [Enduring](../../../shared/reference/glossary.md#enduring) versus [Transient](../../../shared/reference/glossary.md#transient) distinction is a primary determinant of logical decomposition, ownership, integration mapping and lifecycle. It works alongside DDD; it does not mean that every enduring concept or transient relationship has one prescribed code shape.
