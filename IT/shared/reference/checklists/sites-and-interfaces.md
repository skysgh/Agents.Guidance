# Sites and Interfaces Checklist


Use this checklist with [Sites](../catalogues/sites.md) and [Sites, Flows, Views and Components](../catalogues/sites-flows-views-components.md).

- [ ] The groups and connected systems that need the service are named in terms they recognise.
- [ ] Each site has a clear responsibility and curated set of information and capabilities.
- [ ] Groups have been combined where their responsibilities remain coherent, rather than receiving separate sites by default.
- [ ] A site has not been treated as a platform choice such as web, mobile or API technology.
- [ ] Partner user experiences and partner APIs are distinguished where they serve different integration needs.
- [ ] Interoperability is described through a stable contract rather than private implementation access.
- [ ] Each siteÔÇÖs flows are named and connected to the capabilities they coordinate.
- [ ] Each flowÔÇÖs views present one understandable point in the journey.
- [ ] Each component has one primary responsibility as a collection, input or output component.
- [ ] Curated presentation is not being mistaken for authentication or authorisation.
- [ ] Backend boundaries enforce permissions, validation, audit and lifecycle rules.
- [ ] Shared backend capabilities are reused without allowing one siteÔÇÖs presentation needs to redefine another siteÔÇÖs meaning.
